# FPL Team Analyser v2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add richer stats (xG, xA, DefCon, set pieces), opponent weaknesses by position, a component-based forecast v2 tested out-of-sample, and the approved dark-card team view with a click-for-stats panel.

**Architecture:**
- **Data:** new per-player-gameweek stats go in a new table, `player_gw_stats`, alongside v1's `player_gw`. Both the collector and the archive loader fill it, and 2024-25 is loaded as a fitting season.
- **Forecast v2:** SQL views in a new `fpl/sql/forecast_v2.sql`, plus a small Python fitting step that stores per-position calibration factors fitted on 2024-25.
- **Backtest:** extended to score v2, and it picks a forecast source per horizon.
- **App:** the new view is one self-contained HTML/JS block, rendered by `st.components.v1.html` with the squad's data embedded as JSON.

**Tech Stack:** Python 3.11+, SQLite, `requests`, `streamlit` (existing pins), `pytest`. No new dependencies.

**Spec:** `docs/2026-10-20-fpl-v2-design.md` (builds on `docs/2026-10-19-fpl-team-analyser-design.md`; approved layout: `docs/mockups/team-view-cards-v5.html`)

## Global Constraints

- Running cost £0. No new runtime dependencies. No Premier League images: kits are drawn as SVG by the app.
- Every number shown comes from real data. No placeholders in the live app.
- Every forecast component must be explainable in 1–2 sentences, written as a comment at the top of `forecast_v2.sql`.
- Fitted parameters are fitted on `meta.fit_season` (2024-25) and scored on `meta.backtest_season` (2025-26). DefCon chance has no fitted parameters.
- No set-piece bonus in the backtested v2. Set-piece duties are display-only.
- The app uses v2 for a horizon only if its MAE is **strictly lower** than every alternative's on identical rows. Descriptive stats (DefCon chance, clean-sheet chance, weaknesses, the last-6 stats) always show.
- DefCon thresholds: DEF 10+ (clearances, blocks, interceptions, tackles); MID and FWD 12+ (including recoveries). GKs have no DefCon; they show "Clean sheet %" instead.
- Form, weakness and DefCon windows: the last 6 loaded gameweeks before `as_of_gw` (same rule as v1's R12).
- Views use `DROP VIEW IF EXISTS` + `CREATE VIEW`. Every CLI refreshes the caches after applying views. The committed `data/fpl.db` must upgrade safely in place.
- All v1 tests keep passing (118). Tests never touch the network.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A player with no data in the last 6 gameweeks** (new signing, long injury): v2 points, DefCon chance and clean-sheet chance are numbers (0 or position default), never NULL, and the card renders. Pinned in Task 2 `test_v2_new_player_not_null` and Task 4 `test_cards_new_player`.
2. **Blank and double gameweeks in v2:** 0 for a blank, the sum of both fixtures for a double. DefCon chance for a double is "at least one hit" across the two fixtures. Pinned in Task 2 `test_v2_blank_and_double`.
3. **The committed DB from v1** (no new tables or columns): the CLIs and `memory_copy` upgrade it without losing data. Pinned in Task 1 `test_migrate_v1_db`.
4. **Player names with quotes or `</script>`** in the embedded JSON must not break the page or inject HTML. Pinned in Task 5 `test_component_escapes_names`.
5. **Goalkeepers:** no DefCon bar; they show a clean-sheet bar and panel line instead. Pinned in Task 4 `test_cards_goalkeeper_cs` and Task 5 `test_component_gk_label`.

### Task 2: Forecast v2 views

**Files:**
- Create: `fpl/sql/forecast_v2.sql`
- Modify: `fpl/db.py` (`apply_views` runs `forecast.sql`, then `forecast_v2.sql`, then `squad.sql`), `fpl/sql/forecast.sql` (`v_fdr_multiplier` uses `fit_season`), `fpl/sql/schema.sql` (`model_param(name, position, value)`, PK `(name, position)`)
- Test: `tests/test_forecast_v2.py`

**Interfaces:**
- Consumes: `player_gw`, `player_gw_stats`, `fixture`, `player`, `v_player_form` (`start_prob`), `v_last_gw`, `v_target_fixture`, `meta`, `model_param(name, position, value)` (created here in `schema.sql`; missing rows mean factor 1.0).
- Produces these views. Every window is the last 6 loaded gameweeks before `as_of_gw`.
  - `v_team_conceded(season, team_id, as_of_gw, position, pts_pm, xg_pm, defcon_pm)`: per match, FPL points, xG and DefCon hits scored **against** `team_id` by players of `position`. Built from `player_gw` and `player_gw_stats` joined on `opponent_team`.
  - `v_opp_weakness(season, team_id, as_of_gw, position, pts_ratio, xg_ratio, defcon_ratio)`: each value divided by the league average for that position. NULL becomes 1.0.
  - `v_player_threat(season, player_id, as_of_gw, xg90, xa90, defcon_rate, team_xgc_pm)`: `defcon_rate` = `defcon_hits / apps`, or NULL for a GK or when there are no apps.
  - `v_cs_chance(season, player_id, gw, as_of_gw, cs_chance)`: λ = own team's xGC per match × the opponent's attacking ratio (opponent xG for, divided by the league average); `cs_chance = exp(-λ)`, summed per fixture for doubles. SQLite has no `exp`, so use the `math` functions available in Python's sqlite3 (3.35+), or register `exp` in `db.connect` with `conn.create_function` and document that.
  - `v_defcon_chance(season, player_id, gw, as_of_gw, defcon_chance)`: `min(0.95, defcon_rate × defcon_ratio of opponent)`. For a double, `1 − Π(1 − p_fixture)`. 0 for a GK or a blank.
  - `v_xp2(season, player_id, gw, as_of_gw, xp_v2)` for target gw from as_of_gw to as_of_gw+2. Per fixture:
    `start_prob × [ 2 + calib_att(pos) × (xg90 × GOAL_PTS(pos) + xa90 × 3) × xg_ratio(opp, pos) + CS_PTS(pos) × cs_chance + 2 × defcon_chance ]`
    with `GOAL_PTS` GK/DEF 6, MID 5, FWD 4, and `CS_PTS` GK/DEF 4, MID 1, FWD 0. `calib_att` comes from `model_param` (name `calib_att`), default 1.0. A blank gameweek gives 0, and a double sums its fixtures.
  - `v_xp2_next(player_id, xp_v2_next, xp_v2_next3, defcon_chance_next, cs_chance_next)` for the current season and next_gw.
- Put the plain-English explanation of each component as a comment at the top of `forecast_v2.sql`.

### Task 3: Fit, backtest v2 and choose a source per horizon

**Files:**
- Create: `fpl/fit.py`
- Modify: `fpl/backtest.py`, `fpl/sql/forecast.sql` (`v_xp_next`), `fpl/db.py` (`refresh_xp_cache`), `.github/workflows/collect.yml`
- Test: `tests/test_fit.py`, `tests/test_backtest.py`, `tests/test_forecast.py`

**Interfaces:**
- `fit.run(conn) -> dict[str, float]`. Over `fit_season`, gameweeks 6 and later, it fits per position `calib_att = Σ actual attacking points / Σ predicted attacking points` and writes the values to `model_param`. Actual attacking points are goals × GOAL_PTS + assists × 3, from `player_gw_stats`. The predicted values come from v2's attacking term with calib 1.0. Leave 1.0 when the denominator is 0. CLI: `python -m fpl.fit --db data/fpl.db`.
- `backtest.run` adds a `v2` method to both the 1-gameweek and 3-gameweek tables, using the same identical-row rules as before. It writes `meta.forecast_source_1gw` and `meta.forecast_source_3gw`, each one of `'fpl_ep'`, `'model'` or `'v2'`. `'v2'` is chosen only if its MAE is strictly lower than every other method's. Keep `meta.forecast_source` equal to `forecast_source_1gw` for compatibility.
- `backtest.current_season_check(conn) -> dict | None`: scores 1-gameweek methods on the current season's finished gameweeks that have `ep_pre`. It returns None if fewer than 5 such gameweeks exist, and the report then says "pending until enough gameweeks (about GW12)".
- `v_xp_next.xp_next` follows `forecast_source_1gw`, and `xp_next3` follows `forecast_source_3gw` (`'fpl_ep'` uses the R20 scaling). `xp_source` names both, for example `'fpl_ep/v2'`.
- `xp_next_cache` gains `defcon_chance` and `cs_chance` (from `v_xp2_next`).
- Workflow: run `python -m fpl.fit` before the backtest step, with `continue-on-error` like the others.

- `player_cards(conn, analysis: Analysis, suggestions: list[Suggestion]) -> list[dict]`. Returns one dict per squad player, with exactly these keys:
  - `id`, `initials` (first letter of `player.first_name` + first letter of the last word of `player.second_name`), `name`, `full_name`, `pos`, `club` (short_name), `price` (£m float), `owned` (selected_by_percent)

  - `last6`: `{form, xg, xa, defcon_pct}` (form = points per match; `defcon_pct` None for GK)

  - `sell`: None, or `{to_name, to_full_name, to_club, gain3, hit, starts_instead_of}` from the matching `Suggestion`
